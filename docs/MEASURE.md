# 計測の基準値

NeoNote の性能と大きさの実測値を残す。変更の前後でこの表と比べ、数値で判断する。

- 測った日: 2026-11-09
- 環境: Linux x86_64 のコンテナ（共有 CPU。値は揺れる。傾向を見るもので、絶対値は目安）
- ビルド: `cargo build --release`（opt-level=3, LTO, strip）。**Windows と macOS は未計測**（CI の Summary に出る値で埋める）
- 再計測: `cargo test --release perf_ -- --ignored --nocapture --test-threads=1`（`src/neo/perf.rs`）。CI でも同じ計測が回る

## バイナリの大きさ

| 構成 | バイト | 基準との差 |
| --- | --- | --- |
| 正規表現なし（採用前） | 16,138,536 | – |
| regex（最小: `std`, `perf`） | 17,054,312 | +0.87 MiB |
| regex（`unicode-case`, `unicode-perl` あり） **← 採用・既定で有効** | 17,292,072 | +1.10 MiB |
| regex（Unicode 全部） | 17,558,024 | +1.35 MiB |

- 最小の構成では、大文字小文字の無視（`(?i)`）と単語境界（`\b`）が使えない。実用にならないので、両方を足した構成を `Cargo.toml` に書いた。
- 参考: lopdf を足したときの増加は約 1.85 MiB（DESIGN.md）。
- 約 10 MB は同梱フォント（NeoFont）。コード本体の増減は、フォントを除いた差で見ること。

## 検索・全置換（`neo/replace.rs`）

テキストは英数字・日本語・改行が混ざった文書（1 行 約 80 バイト）。単位は ms。

| 文書 | 操作 | 時間 |
| --- | --- | --- |
| 8 MB | `find_all_smart("hello")`（19.5 万件） | 8.4 |
| 8 MB | `find_all_smart("zzzq")`（0 件） | 6.4 |
| 8 MB | `replace_all("hello" → "HELLO")` | 6.0 |
| 50 MB | `find_all_smart("hello")`（122 万件） | 49.0 |
| 50 MB | `find_all_smart("zzzq")`（0 件） | 36.1 |
| 50 MB | `replace_all("hello" → "HELLO")` | 49.4 |

### 全文コピーを無くした前後（検索語が小文字のとき）

| 文書 | 検索語 | 前（全文を小文字化） | 後 |
| --- | --- | --- | --- |
| 50 MB | `hello`（122 万件） | 59 ms | 32 ms |
| 50 MB | `e`（305 万件） | 105 ms | 33 ms |
| 50 MB | `zzzq`（0 件） | 25 ms | 32 ms |

- 一致が多いときは速くなり、**一致が無いときは約 1.3 倍遅い**（標準ライブラリに、先頭バイトを高速に探す関数が無いため）。
- 検索のたびに出ていた、文書と同じ大きさの一時コピー（50 MB の文書で 50 MB）は無くなった。メモリの実測はしていない。
- `memchr` crate を足せば、一致が無いときの遅れは解消する見込み。依存を増やすかは作者が決める。

## 大きな文書の読み込み（項目 5 の判断材料）

### FLTK の TextBuffer だけ（画面なし）

| 文書 | `set_text` | `text()` | `count_lines` | 行数 |
| --- | --- | --- | --- | --- |
| 8 MB | 3.8 ms | 6.8 ms | 5.3 ms | 9.8 万 |
| 50 MB | 64 ms | 71 ms | 35 ms | 61 万 |
| 200 MB | 245 ms | 345 ms | 140 ms | 244 万 |

TextBuffer は、持つだけなら 200 MB でも 1 秒かからない。常駐メモリの増え方は、50 MB で約 +100 MiB、200 MB で約 +200 MiB（1 回の測定。同じプロセスで続けて測ったため、細かくは当てにしない）。

### 実際のアプリ（Xvfb の仮想画面で、引数にファイルを渡して起動）

| ファイル | 開いて落ち着くまでの CPU 時間 | 常駐メモリ | 表示 |
| --- | --- | --- | --- |
| 50 MB | 約 0.3 秒 | 195 MiB | 先頭が出る |
| 200 MB | 約 1.1 秒 | 245 MiB | 先頭が出る（スクリーンショットで確認） |

- 計測した範囲では、200 MB のテキストも固まらずに開ける。**項目 5（大きなファイルの閲覧モード）に着手する根拠は、今のところ無い。**
- 未計測: 打鍵・スクロールの引っかかり、折り返しありでの表示、検索ボックスの入力ごとの時間、Windows と macOS での挙動。普段使いで困る大きさのファイルが見つかったら、ここを足して判断する。
- HEX は 16 MiB で打ち切る仕様（DESIGN.md）。この計測の対象外。

## 表示位置の記憶（動作確認の記録）

Xvfb の仮想画面で、実際のアプリに `xdotool` でキーを送って確かめた（20,000 行のファイル）。

| 操作 | 結果 |
| --- | --- |
| Ctrl+End で末尾へ → Ctrl+W で閉じる → 同じファイルを開き直す | 19,950 行目付近（末尾）が見える |
| 閉じたあとファイルに 1 行足してから開く | 先頭が見える（復元しない） |
| 記録が無い環境で開く | 先頭が見える |

読み込みが速いと、画面の大きさが決まる前にスクロールを頼んで効かないことが、この確認で見つかった。0.1 秒後にもう一度、位置を見える所へ出す処理で直した。

## フォルダ走査とツリーマップ（`neo/archive.rs` の `list_dir`、`ui/treemap.rs` の `build`）

1000 フォルダ × 40 ファイル（4 万 1 千件）。2 コアの Linux、ページキャッシュに載った状態（熱い読み）。単位は ms。`cargo test --release perf_scan -- --ignored --nocapture`。

| 項目 | 変更前 | 変更後 |
| --- | --- | --- |
| `list_dir`（走査 + 並べ替え） | 50 – 54 | 33 – 35（フォルダ単位で並列、最大 8 本） |
| `treemap::build`（木づくり） | 41 – 46 | 5 – 9（子探しを HashMap に） |
| `treemap::build`（1 フォルダに 4 万件 + 2 千フォルダ） | 11.8 | 8.1 |

- 並列化の効果は、ディスクの待ちが長いとき（冷えた読み、HDD、ネットワーク）ほど大きい見込み。冷えた読みは、この環境では測れていない。Windows と macOS も未計測。
- 並べ替えは、パスが重ならないので不安定ソートにした（結果の順序は変わらない）。
